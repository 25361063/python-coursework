# 人机协作报告

## 一、AI 交互日志

### M1 数据处理模块

**1. 数据清洗规则设计**

Prompt："我有一份纽约出租车行程数据，字段包括 fare_amount、trip_distance、passenger_count、trip_duration、payment_type，请设计一套数据清洗方案并编写代码。"

AI 输出了一套完整的过滤逻辑，包括费用 >0 且 <=500、距离 >0 且 <=100 英里、乘客数 1-6 人、行程时长 0-24 小时、支付类型 1-6。代码结构清晰，直接使用了 `pd.DataFrame.query()` 的链式写法。

**采用情况**：阈值全部采用，但发现一处逻辑错误。AI 将过滤条件写为 `fare_amount < 0 and fare_amount > 500`，应为 `or`。运行后清洗数据仅剩几千条（原始数据约 70 万条），通过检查输出行数发现异常，修正逻辑后数据量恢复正常。费用上限 500 美元经后续查阅纽约 TLC 官方数据确认合理，予以保留。

**2. 特征工程**

Prompt："从 pickup_datetime 中提取时间特征，并构建有助于后续建模的衍生变量。"

AI 建议提取 hour、day_of_week、is_weekend、is_rush_hour 四个字段，并计算行程时长（分钟）和平均速度（MPH）。其中 is_rush_hour 的定义为 8:00-10:00 和 17:00-19:00。

**采用情况**：全部采用，但 is_rush_hour 的时段定义存在偏差。在后续撰写报告查阅资料时发现纽约早高峰实际为 7:00-9:00，进行了修正。该错误在功能测试阶段未被发现，因为测试时仅验证了字段是否正确生成，并未验证业务含义的准确性。

**3. 数据质量报告**

Prompt："统计每个关键字段的缺失率和异常值率，生成数据质量报告。"

AI 生成的代码在计算异常值率时，未先排除缺失值再进行异常判断，导致 NaN 同时被计入缺失和异常两个维度，造成重复计数。

**采用情况**：代码整体结构采用，但修复了计算逻辑。运行后部分字段异常率超过 50%，明显不合理，通过逐步 print 中间结果定位到双重计数问题。修正为先 `dropna()` 再统计异常率后，报告数据恢复正常。

### M2 可视化模块

**4. 可视化方案设计**

Prompt："围绕需求分布、区域排名、费用因素、支付方式四个维度设计可视化方案。"

AI 输出了 7 个图表：逐小时订单量对比折线图、Top 10 上下车区域柱状图、Top 5 区域热力图、距离-费用散点图、时段费用箱线图、支付方式分布、地理热力图。

**采用情况**：6 个直接采用，将费用分析的箱线图改为散点图 + 中位数标注的组合形式，原因是散点图能更直观地展示数据密度分布。此为基于报告展示效果的主观判断，非 AI 错误。

**5. geopandas 地理可视化**

Prompt："用 geopandas 读取 taxi_zones.shp，按区域着色展示行程量的空间分布。"

AI 生成的代码能正常运行，但输出的地图存在严重变形——整个纽约市被拉伸为纵向长条。排查后定位到两个问题：（1）坐标系选择错误，AI 使用 `to_crs(epsg=3857)`（Web 墨卡托投影），改为 `to_crs(epsg=2263)`（纽约本地平面坐标系）后变形消失；（2）字段名不匹配，Shapefile 中为 `LocationID`，行程数据中为 `PULocationID`，AI 未进行字段映射导致 merge 失败。

**采用情况**：代码框架采用，手动修正坐标系和字段名。geopandas 库的安装过程也遇到 fiona 与 shapely 的版本冲突问题，该问题无法通过 AI 解决，最终通过查阅 StackOverflow 上的版本兼容性表手动处理。

### M3 建模模块

**6. 时间序列预测方案**

Prompt："设计一个预测每小时出租车订单量的方案，包括特征构建和模型选择。"

AI 建议构建滞后特征（lag 1/2/3 小时）和 3 小时滚动均值，选择随机森林和 Keras 神经网络两个模型进行对比。训练集/测试集划分使用 `sklearn.model_selection.train_test_split(test_size=0.2)`。

**采用情况**：特征构建方案直接采用，滞后特征是我之前未考虑到的，属于 AI 的有效贡献。但数据划分方式存在严重问题——对时间序列数据使用随机划分会导致未来信息泄漏到训练集。初版模型 MAE 仅 12.3，表现异常优秀，正是信息泄漏的结果。修正为按时间顺序前 80% 训练、后 20% 测试后，MAE 上升至 28.7，该数值更能反映模型的真实泛化能力。

**7. 神经网络训练**

Prompt："帮我搭建一个 Keras 全连接网络用于回归预测。"

AI 给出的网络结构为三层 Dense（128-64-32）加 Dropout，学习率设为 0.01。

**采用情况**：网络结构采用，但学习率过高导致训练 loss 在初始阶段剧烈震荡无法收敛。通过观察 loss 曲线发现问题，将学习率调整为 0.001 后训练恢复正常。此外增加了 EarlyStopping 回调以防止过拟合。

### M4 问答系统模块

**8. 规则意图识别**

Prompt："设计基于正则表达式的意图识别系统，覆盖时段查询、区域排名、需求预测、费用估算、数据质量、通用统计六类意图。"

AI 为每类意图编写了正则匹配模式。经测试发现"费用估算"类的匹配过于宽泛，例如"东区的平均车费是多少"会被归类为费用估算而非区域查询，导致调用了错误的处理函数。

**采用情况**：整体框架采用，在"费用估算"的正则中增加了"预估""大概""多少钱"等关键词限定，收窄了匹配范围。该问题通过构造测试用例逐条验证后发现。

**9. LLM API 集成**

Prompt："接入小米 MiMo 大模型 API 作为未识别意图的兜底回答方案。"

AI 给出的代码将 API Key 直接硬编码在源文件中。

**采用情况**：功能逻辑采用，但将密钥读取方式改为 `os.environ.get("MIMO_API_KEY")`，避免敏感信息提交到版本控制。出于本地开发便利性考虑，在代码中保留了默认值作为 fallback。

## 二、三阶段对比

以 **"统计每小时订单量并可视化"** 功能为例，展示三种开发模式的代码差异。

### Native 版（独立编写）

```python
hourly_counts = {}
for _, row in df.iterrows():
    h = row['hour']
    if h in hourly_counts:
        hourly_counts[h] += 1
    else:
        hourly_counts[h] = 1

hours = sorted(hourly_counts.keys())
counts = [hourly_counts[h] for h in hours]

import matplotlib.pyplot as plt
plt.figure(figsize=(10, 5))
plt.bar(hours, counts)
plt.xlabel('Hour')
plt.ylabel('Order Count')
plt.title('Hourly Order Distribution')
plt.xticks(range(0, 24))
plt.show()
```

采用字典逐行累加的方式统计，逻辑清晰但效率低下。`iterrows` 在大数据量下性能很差，且依赖循环而非向量化操作。耗时约 15 分钟，主要花费在确认 `iterrows` 返回值格式上。

### Prompt 版（AI 辅助编写）

```python
import seaborn as sns
import matplotlib.pyplot as plt

hourly = df.groupby('hour').size().reset_index(name='count')
plt.figure(figsize=(10, 5))
sns.barplot(data=hourly, x='hour', y='count')
plt.xlabel('Hour')
plt.ylabel('Order Count')
plt.title('Hourly Order Distribution')
plt.show()
```

使用 `groupby` 实现向量化统计，代码行数减半，运行效率显著提升。引入 seaborn 自动优化了图表样式。耗时约 2 分钟。该版本让我学习到了 `groupby` 的用法，此前我习惯用循环处理分组统计。

### Vibe 版（自然语言对话驱动）

```python
import seaborn as sns
import matplotlib.pyplot as plt

df['day_type'] = df['is_weekend'].map({True: 'Weekend', False: 'Weekday'})
hourly = df.groupby(['hour', 'day_type']).size().reset_index(name='count')

plt.figure(figsize=(12, 5))
sns.lineplot(data=hourly, x='hour', y='count', hue='day_type',
             style='day_type', dashes={'Weekday': '', 'Weekend': (4, 2)},
             linewidth=2)
plt.xlabel('Hour')
plt.ylabel('Order Count')
plt.title('Weekday vs Weekend Hourly Order Pattern')
plt.xticks(range(0, 24))
plt.grid(True, alpha=0.3)
plt.legend(title='Day Type')
plt.show()
```

以自然语言描述需求："分析工作日与周末订单量在 24 小时内的分布差异，折线图，周末用虚线，加图例和网格线。"AI 一次性生成完整代码，包含分组对比、样式区分、图例、网格线等细节。耗时约 1 分钟，额外花费 3 分钟审查代码——`dashes` 参数的元组格式此前未使用过，查阅文档后确认 `(4, 2)` 表示 4 像素实线加 2 像素空白。

### 对比分析

| 维度 | Native 版 | Prompt 版 | Vibe 版 |
|------|-----------|-----------|---------|
| 耗时 | ~15 min | ~5 min | ~5 min（含代码审查） |
| 代码行数 | 15 行 | 9 行 | 15 行 |
| 运行效率 | 低（逐行遍历） | 高（向量化） | 高（向量化） |
| 可扩展性 | 差（改需求需重写） | 好 | 好 |
| 知识增量 | 无新知识 | 学会 groupby | 学会 lineplot 的 style/dashes 参数 |

Native 版的优势在于对每一步逻辑都有完全的掌控，不存在"不知道代码的意思"的问题。Prompt 版在效率和可理解性之间取得了较好的平衡。Vibe 版效率最高，但生成代码中包含我不熟悉的内容，需要额外的审查成本。实际完成作业过程中，Prompt 版是效率和可控性的最优选择。

## 三、反思

### 1. AI 的能力边界：模式匹配强，推理判断弱

完成本次项目后，我对 AI 编程助手的能力边界形成了一个基本判断：**AI 擅长"已知问题的模式匹配"，不擅长"未知问题的推理判断"。**

M2 的图表绘制、M4 的正则编写、M1 的异常值阈值——这些都属于有大量训练样本的标准任务，AI 能快速给出高质量的代码。但 M3 暴露了另一面：AI 对时间序列数据使用了随机划分，导致未来信息泄漏。它并非不知道 `train_test_split` 的功能，而是无法推理出"时间序列具有时序依赖性，不能打乱顺序"这一领域判断。类似的还有 geopandas 坐标系选择——AI 用了通用的 Web 墨卡托投影，而纽约本地数据应使用 epsg:2263 以避免变形。这两个错误的共同点是：调用本身没有问题，问题在于没有根据数据特性做出正确的决策。这意味着使用者如果自身缺乏领域知识，就无法识别 AI 在这类场景中的错误。

### 2. 隐蔽错误比显性 Bug 更危险

本次项目中最具警示意义的发现是：**AI 的错误往往不导致程序崩溃，而是产生看似合理的错误结果。**

M3 随机划分后 MAE 仅 12.3，看起来模型效果很好，但这是信息泄漏造成的虚假数值。修正为按时间顺序划分后 MAE 上升至 28.7，虽然变差了，但才是真实泛化能力。M1 的质量报告中缺失值和异常值双重计数，导致部分字段异常率超过 50%，代码没有报错，只是数字不对。这两个案例揭示了一个共性：传统编程的错误通常表现为崩溃或异常，容易发现；而 AI 的错误是"逻辑正确但语义错误"——代码正常运行，只是结果本身是错的。这意味着"代码能跑"远远不等于"代码正确"，使用者必须具备判断结果合理性的能力。

### 3. Prompt 质量决定输出质量

在协作过程中我逐步认识到：**AI 输出的质量上限由 Prompt 的质量决定。**

M1 是正面案例：仅说"帮我写清洗代码"时 AI 给出通用模板，补充"这是出租车数据，字段有 fare_amount、trip_distance"后 AI 给出了更贴合业务的阈值。M3 是反面案例：未在 Prompt 中说明"这是时间序列数据"，AI 就按通用流程做了随机划分——如果明确指出时序特征，AI 很可能会给出正确方案。从这个角度看，M3 的错误不能完全归咎于 AI，使用者没有提供足够的约束条件也是一个原因。这说明 AI 本质上是"条件概率生成器"，它根据输入推断最可能的输出，而非理解任务的真实意图。使用者需要承担"需求分析"和"上下文提供"的责任，这部分工作无法被 AI 替代。

### 4. 人机协作的合理定位

基于以上认识，我认为 AI 的合理定位是**高效执行者而非决策者**，最有效的模式是"**人判断、AI 实现、人验证**"的三阶段循环。

M1 的数据清洗体现了这一模式的正面效果：我确定阈值（判断），AI 生成代码（实现），我检查输出行数确认合理（验证）。M3 的数据划分则是反面：我将决策权交给 AI，AI 使用了不适用的随机划分，而我最初未验证。两者的区别仅在于"人是否参与了关键决策"，但结果差异显著。

这也意味着 AI 并不能简单地降低编程门槛——它降低了编码实现的门槛，但提高了验证和判断的要求。此外，AI 在环境配置、版本兼容等工程化问题上能力明显不足，geopandas 安装冲突和 tensorflow 兼容性问题最终都靠手动查阅文档解决，AI 给出的方案大多是过时或不适用的。

总结而言，AI 是强大的代码生成工具，但不能替代工程师的核心能力——理解问题、做出判断、验证结果。最理想的状态是由人掌控方向，由 AI 加速执行，再由人确认结果。
